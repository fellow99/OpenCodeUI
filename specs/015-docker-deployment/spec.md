## 1. 模块概述

### 1.1 目的

容器化部署模块提供开箱即用的多服务编排方案，将前端静态资源、后端 API 服务、统一网关和动态端口路由器打包为独立可部署单元。用户通过一条命令即可启动完整的应用栈。

### 1.2 解决的问题

- **一键部署**：完整的前后端服务编排，无需手动配置各组件间的网络连接
- **统一入口**：通过网关聚合所有服务，对外暴露单一访问地址
- **独立部署**：前端可脱离后端单独运行，连接已有的后端实例
- **开发服务预览**：容器内运行的开发服务自动被发现并生成可访问的预览链接
- **数据持久化**：容器重建后保留配置、会话和工具链运行时
- **安全加固**：支持基础认证，满足公网部署的安全要求

### 1.3 范围

本模块涵盖：

- 多服务编排定义（网关、前端、后端、路由器）
- 网关路由规则与协议代理（REST、SSE、WebSocket）
- 独立前端部署模式
- 环境变量配置体系
- 数据卷持久化策略
- 容器启动时的工具链自愈
- 动态端口扫描与预览链接生成
- 外部反向代理参考配置

本模块不涵盖：

- 镜像构建流水线的具体实现（由 CI/CD 负责）
- 桌面应用的打包与分发
- 本地开发环境的启动流程

## 3. 功能需求

### FR-01：多服务编排

**描述**：完整部署模式包含四个服务，通过内部网络互联，由编排文件统一定义生命周期和依赖关系。

**要求**：

- 网关服务作为唯一对外入口，依赖前端和后端服务就绪后启动
- 前端服务提供静态资源，无外部端口暴露，仅对内网可见
- 后端服务暴露 API 端口，挂载工作目录和用户数据卷
- 所有服务加入同一内部网络，通过服务名称互相发现
- 前端和后端使用预构建镜像，网关镜像内嵌路由器二进制

**验收标准**：

- 给定正确的环境变量，单条命令启动全部服务
- 网关在前端和后端就绪后才开始接受请求
- 服务间通过内部网络通信，不暴露多余端口到宿主机

### FR-02：网关路由

**描述**：网关作为统一入口，根据请求路径将流量分发到对应的后端服务。

**要求**：

- `/api/*` 路径转发到后端 API 服务，支持 SSE 流式响应
- `/routes` 和 `/preview/*` 路径转发到路由器服务
- 其余所有请求转发到前端静态服务
- 主入口端口和预览端口分离，各自独立监听

**验收标准**：

- 给定 `/api/sessions` 请求，返回后端会话列表
- 给定 `/routes` 请求，返回路由管理界面
- 给定 `/` 请求，返回前端首页
- SSE 连接保持活跃，不因代理缓冲而中断

### FR-03：独立前端模式

**描述**：前端可单独部署为独立服务，直接暴露端口并反向代理到外部后端。

**要求**：

- 仅启动前端服务，不包含网关和后端
- 通过环境变量指定外部后端地址
- 自动处理宿主机到容器网络的地址解析
- `/api/*` 路径剥离前缀后转发到外部后端，支持 SSE

**验收标准**：

- 给定外部后端地址，前端正常连接并渲染应用
- 给定 Linux 环境，自动配置宿主机网关地址解析
- API 请求正确转发，SSE 流式响应正常

### FR-04：环境变量配置

**描述**：所有运行时参数通过环境变量注入，提供示例配置文件作为模板。

**要求**：

- LLM 提供商 API Key 至少填写一个，支持多家提供商
- 端口参数可自定义，含合理默认值
- 工作目录路径可配置，映射到容器内固定路径
- 安全认证参数（用户名和密码）用于保护公网部署
- 路由器参数（扫描间隔、端口范围、排除端口）可调整

**验收标准**：

- 给定最小配置（仅一个 API Key），服务正常启动
- 未设置的参数使用内置默认值
- 敏感参数未设置时，服务仍可启动但功能受限

### FR-05：数据持久化

**描述**：通过命名卷持久化关键数据，确保容器重建后状态不丢失。

**要求**：

- 后端用户数据卷挂载到用户主目录，包含配置、会话缓存、工具链和包管理器缓存
- 路由器状态卷保存动态路由配置
- 工作目录通过绑定挂载映射，支持宿主机文件编辑
- 容器启动入口脚本自动检测并修复缺失的工具链

**验收标准**：

- 给定容器停止后重新启动，所有会话和配置保留
- 给定容器完全重建，用户数据卷中的内容不丢失
- 工作目录中的文件变更在宿主机和容器间同步

### FR-06：SSE 与 WebSocket 代理

**描述**：网关正确代理流式协议，确保实时通信不被缓冲或截断。

**要求**：

- API 代理禁用响应缓冲，启用即时刷新
- WebSocket 连接支持协议升级
- 外部反向代理场景下，提供 Nginx 和 Caddy 的参考配置
- 连接超时时间设置足够长，支持长时间运行的任务

**验收标准**：

- 给定 SSE 连接，消息逐条到达而非批量返回
- 给定 WebSocket 终端连接，双向通信正常
- 给定 Nginx 反向代理，SSE 和 WebSocket 均正常工作

### FR-07：动态端口路由

**描述**：路由器自动扫描容器内指定范围的 HTTP 服务端口，生成带令牌的安全访问链接。

**要求**：

- 可配置扫描间隔，定期检测新启动的服务
- 可配置端口扫描范围，默认覆盖常用开发端口
- 可排除特定端口（如后端 API 端口）
- 通过令牌化路径生成预览链接，防止未授权访问
- 路由状态持久化到卷中，重启后恢复

**验收标准**：

- 给定容器内新启动的服务在扫描范围内，自动生成预览链接
- 给定排除的端口，不为其生成预览链接
- 预览链接包含随机令牌，无法猜测
- 路由器重启后，已注册的路由规则恢复

### FR-08：安全认证

**描述**：公网部署时支持为基础认证保护关键端点。

**要求**：

- 用户名和密码通过环境变量配置
- 认证信息同时应用于后端服务和路由器管理面板
- 未设置密码时，服务仍可启动（适用于内网环境）
- 公网部署文档明确提示必须设置认证

**验收标准**：

- 给定已配置的用户名和密码，访问受保护端点需要认证
- 给定未设置密码，服务正常启动但无认证保护
- 认证信息在所有服务间一致

## 4. 服务架构

### 4.1 服务拓扑

```
                    ┌─────────────────────────────────────┐
                    │           外部反向代理（可选）         │
                    │         Nginx / Caddy + HTTPS        │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │              Gateway                 │
                    │  主入口 :6658  │  预览入口 :6659     │
                    │  ┌───────────┴───────────────────┐  │
                    │  │  内嵌路由器 :7070              │  │
                    │  │  动态端口发现 + 预览链接生成    │  │
                    │  └───────────────────────────────┘  │
                    └──────┬───────────────┬──────────────┘
                           │               │
              ┌────────────▼───┐   ┌───────▼────────────┐
              │   Frontend     │   │     Backend        │
              │   静态资源      │   │   API 服务          │
              │   :3000（内）   │   │   :4096（内）       │
              └────────────────┘   └────────────────────┘
```

### 4.2 服务清单

| 服务     | 对外端口               | 内部端口 | 说明                           |
| -------- | ---------------------- | -------- | ------------------------------ |
| Gateway  | 6658（`GATEWAY_PORT`） | 6658     | 统一入口，反向代理所有请求     |
| Gateway  | 6659（`PREVIEW_PORT`） | 6659     | 开发服务预览专用端口           |
| Frontend | 不暴露                 | 3000     | 静态前端资源                   |
| Backend  | 不暴露                 | 4096     | API 服务                       |
| Router   | 不暴露                 | 7070     | 动态端口路由（内嵌于 Gateway） |

### 4.3 网络拓扑

- 所有服务加入同一内部网络 `opencode-net`
- 仅 Gateway 的端口映射到宿主机（绑定 `127.0.0.1`）
- 服务间通过服务名称进行 DNS 解析
- Gateway 需要访问宿主机 Docker 套接字以支持动态端口发现

### 4.4 数据卷

| 卷名                   | 挂载目标          | 用途                       |
| ---------------------- | ----------------- | -------------------------- |
| `opencode-home`        | 后端 `/root`      | 配置、会话、工具链、包缓存 |
| `opencode-router-data` | Gateway `/data`   | 路由器状态文件             |
| 工作目录（绑定挂载）   | 后端 `/workspace` | 用户工作区文件             |

## 7. 容器启动流程

### 7.1 后端入口脚本

后端容器启动时执行以下自检流程：

1. 检查核心工具链是否可用
2. 如果不可用，尝试从持久化卷中恢复
3. 如果恢复失败，从网络重新安装
4. 所有工具就绪后，执行传入的启动命令

此流程确保容器重建后工具链自动恢复，无需手动干预。

### 7.2 网关入口脚本

网关容器同时启动两个进程：

1. 路由器进程：负责端口扫描和动态路由生成
2. Web 服务进程：负责请求代理和静态资源分发

两个进程通过信号协调生命周期，任一进程退出时另一个也随之终止。

## 8. 验收场景

### 场景 1：完整部署

**前置条件**：已克隆项目仓库，已复制并填写环境变量文件

**步骤**：

1. 执行 `compose up -d` 启动全部服务
2. 等待所有服务进入运行状态
3. 浏览器访问 `http://localhost:6658`

**预期结果**：

- 四个服务全部处于运行状态
- 网关在前端和后端就绪后才开始响应
- 浏览器显示应用首页
- API 请求正常返回数据

### 场景 2：独立前端部署

**前置条件**：已有运行中的后端服务在 `localhost:4096`

**步骤**：

1. 执行 `compose -f compose.standalone.yml up -d`
2. 浏览器访问 `http://localhost:3000`

**预期结果**：

- 仅前端容器启动
- 前端成功连接到外部后端
- 应用功能完整可用

### 场景 3：连接远程后端

**前置条件**：远程后端运行在 `remote-server.com:4096`

**步骤**：

1. 设置 `BACKEND_URL=remote-server.com:4096`
2. 启动独立前端部署

**预期结果**：

- 前端连接到远程后端
- 所有 API 请求正确转发到远程地址

### 场景 4：数据持久化

**前置条件**：完整部署已运行，已创建会话并安装工具链

**步骤**：

1. 执行 `compose down` 停止所有服务
2. 执行 `compose up -d` 重新启动
3. 检查之前的会话是否保留

**预期结果**：

- 所有历史会话仍然存在
- 已安装的工具链无需重新安装
- 工作目录文件保持不变

### 场景 5：动态端口预览

**前置条件**：完整部署已运行

**步骤**：

1. 在后端容器中启动一个 HTTP 服务（如 `python -m http.server 8000`）
2. 等待路由器扫描周期完成
3. 访问预览端口 `6659` 上生成的令牌化路径

**预期结果**：

- 路由器自动发现新端口
- 生成带令牌的预览链接
- 通过预览链接可访问该服务

### 场景 6：SSE 流式响应

**前置条件**：完整部署已运行

**步骤**：

1. 在应用中发起一个需要 AI 回复的请求
2. 观察响应方式

**预期结果**：

- 回复内容逐字到达，而非等待完成后一次性返回
- 连接保持活跃直到回复完成
- 无缓冲导致的延迟

### 场景 7：安全认证

**前置条件**：已设置 `OPENCODE_SERVER_USERNAME` 和 `OPENCODE_SERVER_PASSWORD`

**步骤**：

1. 访问路由管理面板 `/routes`
2. 不提供认证信息

**预期结果**：

- 请求被拒绝，返回 401 状态码
- 提供正确的用户名和密码后可正常访问

### 场景 8：容器重建后工具链恢复

**前置条件**：已通过 `mise` 安装了 Node 和 Python 运行时

**步骤**：

1. 强制删除后端容器
2. 重新启动服务
3. 进入容器检查已安装的工具

**预期结果**：

- 入口脚本自动检测到工具缺失
- 从持久化卷恢复或重新安装
- 工具版本与安装前一致

## 10. 架构决策记录

### ADR-001：为什么网关同时运行两个进程

**决策**：网关容器内同时运行 Web 服务进程和路由器进程，通过入口脚本协调生命周期。

**理由**：

- 路由器需要与 Web 服务共享配置和状态文件
- 避免额外的容器间网络延迟
- 简化部署拓扑，减少服务数量
- 两个进程同生共死，避免孤立进程

### ADR-002：为什么后端只保留单一持久化卷

**决策**：后端仅使用一个命名卷挂载到用户主目录，而非拆分为配置、缓存、工具等多个小卷。

**理由**：

- 简化卷管理，降低运维复杂度
- 用户主目录天然包含所有用户态数据
- 入口脚本的自愈机制弥补了粗粒度卷的不足
- 旧版本的多个卷在迁移后变为孤立卷，可安全清理

### ADR-003：为什么预览端口与主入口分离

**决策**：预览服务使用独立端口（6659），与主应用端口（6658）分离。

**理由**：

- 预览服务面向容器内开发服务，安全模型不同
- 独立端口可绑定独立域名，解决前端资源路径问题
- 避免预览流量影响主应用的稳定性
- 公网部署时可对预览端口施加不同的访问控制

### ADR-004：为什么服务端口绑定 127.0.0.1

**决策**：网关的对外端口仅绑定到 `127.0.0.1`，不监听所有网络接口。

**理由**：

- 强制要求公网部署时在前端放置反向代理
- 避免容器直接暴露在外部网络
- 反向代理可统一处理 HTTPS、限流、日志等横切关注点

## 11. 风险与缓解

| 风险                          | 影响                      | 缓解措施                                      |
| ----------------------------- | ------------------------- | --------------------------------------------- |
| Docker 套接字挂载带来安全风险 | 容器内可控制宿主机 Docker | 以只读方式挂载，仅用于端口发现                |
| 工具链在线安装失败            | 后端容器启动失败          | 入口脚本多级回退：检查 PATH、恢复卷、网络安装 |
| 路由器扫描间隔过长            | 新启动的服务延迟被发现    | 可配置扫描间隔，默认 5 秒                     |
| 预览令牌被泄露                | 未授权用户访问开发服务    | 令牌长度可配置（默认 12 位），定期轮换        |
| 未设置认证密码即公网部署      | 服务暴露于未授权访问      | 文档明确警告，环境变量示例中标注必填          |
| 旧版本多卷迁移数据丢失        | 升级后历史数据不可用      | 入口脚本不主动清理旧卷，用户确认后再手动删除  |
