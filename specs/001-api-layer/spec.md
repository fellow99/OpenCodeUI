## 1. 模块概述

### 1.1 目的

API 通信层是前端与 OpenCode 后端之间的唯一通信通道。它封装了所有与后端交互的细节，向上层业务模块提供统一、类型安全、环境自适应的调用接口。

### 1.2 解决的问题

- **多协议统一**：REST 调用、SSE 事件流、WebSocket 终端连接，三种协议由同一层管理
- **双环境适配**：浏览器环境与桌面应用环境使用不同的底层传输机制，上层无感知
- **多服务器管理**：支持配置多个后端服务器，运行时可切换，连接自动重建
- **目录作用域**：所有 API 调用支持目录参数，实现多项目隔离
- **连接韧性**：SSE 断线自动重连、心跳检测、后台保活、网络状态感知

### 1.3 范围

本模块涵盖：

- SDK 客户端的创建、缓存与失效
- REST API 调用的统一封装（会话、消息、文件、权限、终端等 16 个业务域）
- SSE 事件订阅的 singleton 连接管理
- WebSocket 终端连接的 URL 构建
- 错误解包与类型化错误处理
- 服务器切换时的连接重建

本模块不涵盖：

- 具体的 UI 组件实现
- 业务状态管理（由状态管理层负责）
- 后端 API 的具体实现

## 3. 功能需求

### FR-01：基于 SDK 的 HTTP 客户端，自动注入认证头

**描述**：所有 REST API 调用通过统一的 SDK 客户端发起，客户端根据当前活动服务器自动构建 base URL 和 Authorization 请求头。

**要求**：

- SDK 客户端按 "base URL + 认证信息" 组合进行缓存，相同组合复用同一实例
- 认证信息采用 Basic Auth 格式，仅在配置了密码时添加 Authorization 头
- 服务器切换时，旧客户端实例失效，新实例自动创建
- 提供同步和异步两种客户端获取方式，异步方式确保桌面环境的原生 HTTP 模块已加载

**验收标准**：

- 给定已配置密码的服务器，所有 API 请求自动携带 Authorization 头
- 给定未配置密码的服务器，API 请求不携带 Authorization 头
- 切换服务器后，新请求使用新服务器的 URL 和认证信息

### FR-02：SSE 单例连接，支持自动重连

**描述**：全局维护唯一的 SSE 事件流连接，多个订阅者共享同一连接。连接断开后按指数退避策略自动重连。

**要求**：

- 首个订阅者注册时建立连接，最后一个订阅者注销时断开连接
- 重连延迟采用分级策略：1s, 2s, 3s, 5s, 10s, 30s
- 后台模式下使用更激进的重连策略：500ms, 1s, 2s, 3s, 5s, 10s
- 心跳超时检测：前台 60 秒无事件视为连接死亡，后台 120 秒
- 后台保活轮询：每 30 秒检查一次连接活性
- 连接代次机制：每次重连递增代次，旧连接的事件自动丢弃

**验收标准**：

- 给定 10 个组件同时订阅事件，仅建立 1 条 SSE 连接
- 给定网络断开后恢复，SSE 连接在 30 秒内自动重建
- 给定应用在后台运行 5 分钟后回到前台，连接状态正确恢复

### FR-03：WebSocket 连接用于终端通信

**描述**：终端（PTY）通过 WebSocket 协议与后端建立双向实时通信。

**要求**：

- WebSocket URL 基于当前活动服务器的 HTTP URL 自动转换（http 转 ws，https 转 wss）
- 认证信息通过 URL userinfo 方式传递（WebSocket 不支持自定义请求头）
- 目录参数通过查询字符串传递
- 连接 URL 的构建与 SDK 客户端解耦

**验收标准**：

- 给定已配置密码的服务器，WebSocket URL 包含 userinfo 部分
- 给定未配置密码的服务器，WebSocket URL 不包含 userinfo 部分
- 目录参数正确编码为查询字符串

### FR-04：目录作用域的 API 调用

**描述**：所有 API 调用支持可选的目录参数，用于指定操作的工作目录，实现多项目数据隔离。

**要求**：

- 目录参数在所有 API 函数中为可选参数
- 目录路径在发送前进行标准化处理
- 根目录列表结果按 "服务器 ID + 目录" 组合进行缓存，缓存有效期 10 秒
- 并发请求同一目录时，仅发起一次实际网络请求

**验收标准**：

- 给定目录参数，API 返回该目录下的数据
- 未给定目录参数，API 返回默认目录的数据
- 短时间内多次请求同一根目录，仅产生一次网络请求

### FR-05：错误解包与类型化错误处理

**描述**：SDK 返回的结果包含 data 和 error 两个字段，上层需要的是解包后的纯数据。

**要求**：

- 提供统一的解包函数，从 SDK 返回值中提取 data 字段
- 如果存在 error，将其转换为标准 Error 对象并抛出
- 支持 Error 实例、字符串、JSON 对象三种错误格式

**验收标准**：

- 给定成功的 SDK 调用，解包函数返回 data 字段
- 给定失败的 SDK 调用，解包函数抛出包含错误信息的 Error 对象

### FR-06：桌面环境兼容的 HTTP 传输

**描述**：在桌面应用环境中，使用原生 HTTP 插件替代浏览器 fetch，以绕过浏览器的跨域限制。

**要求**：

- 自动检测运行环境（浏览器或桌面）
- 桌面环境中，SDK 客户端使用原生 HTTP 插件的 fetch 实现
- 原生 HTTP 模块采用懒加载，仅在需要时导入
- 提供异步初始化方法，确保应用启动时原生模块已就绪

**验收标准**：

- 给定桌面环境，API 调用使用原生 HTTP 传输
- 给定浏览器环境，API 调用使用标准 fetch
- 原生模块加载完成前，已有请求使用默认 fetch 不阻塞

### FR-07：客户端缓存按服务器 URL 和认证信息区分

**描述**：SDK 客户端实例按 "base URL + 认证信息" 组合进行缓存，避免重复创建。

**要求**：

- 缓存键由 base URL 和认证信息拼接而成
- 服务器切换或认证信息变更时，缓存失效
- 提供强制失效接口，供外部主动触发缓存清理

**验收标准**：

- 给定相同的服务器和认证信息，多次获取客户端返回同一实例
- 给定不同的服务器，获取客户端返回不同实例
- 调用强制失效后，下次获取客户端返回新实例

## 4. 关键实体

### 4.1 SDK 客户端

| 属性    | 说明                                           |
| ------- | ---------------------------------------------- |
| baseUrl | 后端服务地址                                   |
| headers | 请求头（含可选的 Authorization）               |
| fetch   | HTTP 传输函数（浏览器 fetch 或桌面原生 fetch） |

**行为**：

- 按缓存键复用实例
- 支持强制失效重建
- 所有 REST 调用通过此客户端发起

### 4.2 事件订阅

| 属性            | 说明                                                          |
| --------------- | ------------------------------------------------------------- |
| callbacks       | 事件回调集合，包含 20+ 种事件类型的处理函数                   |
| connectionState | 当前连接状态（connecting / connected / disconnected / error） |
| generation      | 连接代次，用于区分新旧连接的事件                              |

**行为**：

- 多订阅者共享单例连接
- 订阅时自动启动连接，取消订阅时自动清理
- 事件按类型分发到对应的回调函数

### 4.3 连接状态

| 状态         | 说明                   |
| ------------ | ---------------------- |
| connecting   | 正在建立连接           |
| connected    | 连接已建立，心跳正常   |
| disconnected | 连接已断开，等待重连   |
| error        | 连接发生错误，等待重连 |

**可观测属性**：

- lastEventTime：最后一次收到事件的时间戳
- reconnectAttempt：当前重连尝试次数
- error：错误描述信息

### 4.4 PTY 连接

| 属性      | 说明               |
| --------- | ------------------ |
| ptyId     | 终端会话唯一标识   |
| wsUrl     | WebSocket 连接地址 |
| directory | 工作目录           |

**行为**：

- URL 由 HTTP base URL 自动转换
- 认证信息通过 URL userinfo 传递
- 连接生命周期由终端组件自行管理

### 6.2 单例模式

SSE 连接采用单例模式：

- 全局仅维护一条 SSE 连接
- 首个订阅者注册时启动连接
- 最后一个订阅者注销时断开连接
- 所有订阅者共享连接状态和事件流

### 6.3 重连策略

**正常模式重连延迟**：

| 尝试次数 | 延迟  |
| -------- | ----- |
| 1        | 1 秒  |
| 2        | 2 秒  |
| 3        | 3 秒  |
| 4        | 5 秒  |
| 5        | 10 秒 |
| 6+       | 30 秒 |

**后台模式重连延迟**：

| 尝试次数 | 延迟     |
| -------- | -------- |
| 1        | 500 毫秒 |
| 2        | 1 秒     |
| 3        | 2 秒     |
| 4        | 3 秒     |
| 5        | 5 秒     |
| 6+       | 10 秒    |

### 6.4 生命周期感知

| 事件               | 行为                                         |
| ------------------ | -------------------------------------------- |
| 页面可见性变为可见 | 检查连接活性，必要时立即重连                 |
| 页面可见性变为隐藏 | 切换为后台模式（更长心跳超时、启动保活轮询） |
| 网络恢复在线       | 若当前未连接，立即重连                       |
| 网络断开离线       | 断开现有连接，停止重连计时器                 |

### 6.5 桌面环境桥接

在桌面环境中，SSE 连接通过 Rust 侧的 reqwest + Channel 机制桥接：

- 前端调用 Rust 命令启动 SSE 流
- 事件通过 Channel 实时推送到前端
- 断开连接时调用对应的 Rust 命令
- 多次并发断开调用自动串行化

## 7. 验收场景

### 场景 1：成功的 API 调用

**前置条件**：后端服务正常运行，服务器已配置

**步骤**：

1. 调用获取会话列表的 API
2. 等待响应

**预期结果**：

- 请求自动携带当前服务器的 base URL
- 如果配置了密码，请求携带 Authorization 头
- 返回解包后的会话列表数据
- 不抛出异常

### 场景 2：SSE 断线后自动重连

**前置条件**：SSE 连接已建立，至少有一个活跃订阅者

**步骤**：

1. 模拟网络断开（后端服务停止）
2. 等待 1 秒
3. 恢复网络（后端服务重启）

**预期结果**：

- 连接状态变为 disconnected 或 error
- 1 秒后自动发起重连尝试
- 后端恢复后连接状态变为 connected
- 订阅者收到 onReconnected 回调，原因为 'network'
- 重连计数重置为 0

### 场景 3：服务器切换

**前置条件**：存在多个已配置的服务器，SSE 连接已建立

**步骤**：

1. 将活动服务器从 Server A 切换到 Server B
2. 等待 SSE 重连完成

**预期结果**：

- SDK 客户端缓存失效
- SSE 连接断开并使用 Server B 的 URL 重新建立
- 订阅者收到 onReconnected 回调，原因为 'server-switch'
- 后续所有 API 调用指向 Server B

### 场景 4：无订阅者时不建立连接

**前置条件**：无活跃订阅者

**步骤**：

1. 检查 SSE 连接状态

**预期结果**：

- 连接状态为 disconnected
- 不发起任何网络连接
- 不消耗网络资源

### 场景 5：后台模式下的连接保活

**前置条件**：SSE 连接已建立，应用进入后台

**步骤**：

1. 应用进入后台（页面不可见）
2. 等待 30 秒
3. 应用回到前台

**预期结果**：

- 后台期间心跳超时切换为 120 秒
- 后台保活轮询每 30 秒检查一次连接活性
- 如果连接已死亡，后台期间主动触发重连
- 回到前台时连接状态正确

### 场景 6：目录作用域隔离

**前置条件**：后端服务运行，存在多个工作目录

**步骤**：

1. 调用获取会话列表，指定目录 A
2. 调用获取会话列表，指定目录 B
3. 调用获取会话列表，不指定目录

**预期结果**：

- 步骤 1 返回目录 A 下的会话
- 步骤 2 返回目录 B 下的会话
- 步骤 3 返回默认目录下的会话
- 三次调用互不干扰

## 9. 架构决策记录

### ADR-001：为什么 SSE 使用单例而非多连接

**决策**：全局维护唯一的 SSE 连接，所有订阅者共享。

**理由**：

- 后端对每个目录仅维护一条事件流，多连接无额外收益
- 减少服务器资源消耗
- 简化连接状态管理
- 避免多连接间的事件重复和乱序

### ADR-002：为什么 WebSocket 认证通过 URL userinfo

**决策**：WebSocket 连接将认证信息编码到 URL 的 userinfo 部分。

**理由**：

- WebSocket 协议不支持自定义请求头
- URL userinfo 是标准的认证传递方式
- 后端已支持从 URL 解析认证信息

### ADR-003：为什么 SDK 返回值需要解包

**决策**：提供统一的 unwrap 函数，将 SDK 的 { data, error } 格式转换为直接返回 data 或抛出 error。

**理由**：

- SDK 的设计是始终返回 { data, error } 结构
- 上层业务逻辑期望直接获取数据或捕获异常
- 统一解包避免每个调用点重复编写错误检查逻辑

### ADR-004：为什么桌面环境使用独立的 SSE 桥接

**决策**：桌面环境中 SSE 通过 Rust 侧的 reqwest + Channel 实现，而非浏览器 fetch。

**理由**：

- 桌面环境的 fetch 实现（plugin-http）对 SSE 流式读取支持有限
- Rust 侧的 reqwest 对 SSE 有更好的原生支持
- Channel 机制提供可靠的事件推送通道

## 10. 风险与缓解

| 风险                        | 影响                                  | 缓解措施                                |
| --------------------------- | ------------------------------------- | --------------------------------------- |
| 移动端后台 timer 被系统冻结 | 心跳检测失效，连接静默断开            | 后台保活轮询 + 页面可见性恢复时强制检查 |
| 服务器切换时旧连接事件泄漏  | 旧服务器的事件被错误分发              | 连接代次机制，旧代次事件自动丢弃        |
| 并发断开/连接请求竞争       | Rust 侧 connect/disconnect 状态不一致 | 断开操作串行化，确保先断开再连接        |
| 根目录缓存过期导致数据陈旧  | 用户看到过时的文件列表                | 10 秒 TTL + 并发请求去重                |
