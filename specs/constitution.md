# OpenCodeUI 项目宪法

> 本文档定义 OpenCodeUI 的核心原则、设计哲学与不可妥协的约束条件。所有架构决策、功能开发和代码审查均须遵循本宪法。

---

## 原则 1：AI 驱动开发（Vibe Coding）

**声明**：本项目 100% 由 AI 辅助编程完成，所有代码通过对话驱动开发产生。

**理由**：OpenCodeUI 从第一行代码到最终发布，全部依赖 AI 对话生成。这不是权宜之计，而是项目的根本开发范式。选择 Vibe Coding 意味着我们接受 AI 作为一等公民的协作者，而非辅助工具。开发流程围绕"描述需求. AI 生成. 人工审查"的循环展开，而非传统的"手写代码"模式。

---

## 原则 2：OpenCode 兼容性优先

**声明**：前端必须忠实实现 OpenCode 后端的全部能力，不遗漏、不曲解、不越界。

**理由**：OpenCodeUI 是 OpenCode 的第三方前端，其存在价值在于为后端提供完整的用户界面。前端的功能边界由后端 API 决定，而非前端自行扩展。所有 API 调用必须与 OpenCode 的接口规范保持一致，使用官方 SDK（`@opencode-ai/sdk`）而非自行封装。

---

## 原则 3：多平台统一代码库

**声明**：Web 端（Docker/独立部署）与桌面端（Tauri）共享同一套前端代码，不因平台差异分裂代码库。

**理由**：项目同时提供 Web 部署和 Tauri 桌面客户端两种形态。平台差异通过条件编译和平台适配层处理，核心业务逻辑、UI 组件、状态管理必须保持统一。`src/` 为共享代码，`src-tauri/` 仅包含平台特定的 Rust 桥接代码。

---

## 原则 4：自定义优于框架依赖

**声明**：优先实现轻量级自定义方案，而非引入重量级第三方框架。最小化依赖，最大化控制力。

**理由**：项目选择自定义路由而非 react-router，自定义状态管理而非 Redux/Zustand。每个额外依赖都增加构建体积、引入潜在 bug、降低代码可控性。只有在功能复杂度高且社区方案成熟时才考虑引入外部库（如 xterm.js、Shiki）。

---

## 原则 5：实时通信优先

**声明**：SSE（Server-Sent Events）是前后端数据流的主要通道，轮询仅作为降级方案。

**理由**：OpenCode 后端通过 SSE 推送 AI 生成的流式响应。前端必须以 SSE 事件为第一优先级，确保用户实时看到 AI 的思考过程和输出。反向代理配置中必须保留 SSE 支持（Nginx `proxy_buffering off`，Caddy `flush_interval -1`）。

---

## 原则 6：中文优先文档

**声明**：项目文档以中文为第一语言，英文为次要翻译版本。

**理由**：项目的主要用户群体和贡献者来自中文社区。README.md 以中文为主体，英文版本（README_EN.md）为翻译产物。代码注释、提交信息、Issue 讨论默认使用中文。

---

## 原则 7：开源与社区驱动

**声明**：本项目采用 GPL-3.0 许可证，代码完全透明，欢迎社区贡献。

**理由**：GPL-3.0 确保衍生作品同样开源，保护项目的自由软件属性。项目处于早期阶段，通过 GitHub Issues 和 Pull Requests 接受社区反馈。所有代码变更须通过 CI 校验（TypeScript 检查、ESLint、单元测试、生产构建）。

---

## 原则 8：零配置用户体验

**声明**：用户应能通过最少操作启动系统。Docker 部署做到 `docker compose up -d` 即可运行，同时提供开箱即用的托管版本。

**理由**：降低使用门槛是项目推广的关键。完整部署仅需克隆仓库、复制环境变量、启动容器三步。同时提供 GitHub Pages 托管版，用户只需启动本地 OpenCode 后端并指定 CORS 即可直接使用，无需部署前端。

---

## 原则 9：主题与可访问性

**声明**：提供多主题支持（Eucalyptus/Claude/Breeze），完整的明暗模式切换，移动端响应式布局。

**理由**：开发者对界面审美有差异化需求，主题系统允许用户选择最舒适的视觉风格。移动端适配确保安全区域、触摸优化、响应式布局，使 OpenCodeUI 可在手机和平板上使用。PWA 支持允许用户将应用安装到桌面或移动设备。

---

## 原则 10：模块化功能架构

**声明**：每个功能模块（chat、message、session、settings、mention、slash-command）必须自包含、低耦合、可独立理解。

**理由**：项目采用 Feature-Sliced 风格的目录组织，`src/features/` 下每个子目录对应一个完整功能。模块内部包含自身的组件、逻辑和样式，模块间通过明确的接口通信。这种结构便于 AI 理解上下文、新人快速定位代码、以及功能的独立测试和维护。

---

## 约束条件

以下约束为不可妥协的底线：

| 编号 | 约束       | 说明                                                                     |
| ---- | ---------- | ------------------------------------------------------------------------ |
| C1   | 许可证     | 必须保持 GPL-3.0，不得更改                                               |
| C2   | 后端依赖   | 必须兼容 OpenCode 后端，不可绑定其他后端                                 |
| C3   | 构建校验   | 所有 PR 必须通过 `npm run validate`（TypeScript + ESLint + 测试 + 构建） |
| C4   | 依赖最小化 | 新增依赖需经过充分论证，禁止引入功能重叠的库                             |
| C5   | SSE 支持   | 任何部署方案不得破坏 SSE 流式通信                                        |
