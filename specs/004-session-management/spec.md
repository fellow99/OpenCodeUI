# 会话管理模块规范

> 模块编号：004-session-management
> 状态：已实现
> 最后更新：2026-04-12

---

## 1. 模块概述

### 1.1 目的

会话管理模块负责会话的完整生命周期，包括创建、恢复、分叉、删除、分享、总结、回退等核心操作。它为前端提供会话列表浏览、活跃状态追踪、子会话管理、项目作用域隔离以及会话统计等能力。

### 1.2 解决的问题

- **会话生命周期管理**：从创建到删除的完整流程，包含中间态（分叉、回退、归档）
- **多项目隔离**：会话按工作目录/项目分组，支持全局视图与项目视图切换
- **活跃状态追踪**：实时显示哪些会话正在工作、等待用户输入或发生错误
- **子会话管理**：父会话可以派生子任务（子 Agent），子会话的权限请求冒泡到父界面
- **消息回退与重做**：支持撤销已发送的用户消息及其后续 AI 回复，并可逐步恢复
- **会话统计**：计算 Token 消耗、费用、上下文使用率等指标

### 1.3 范围

本模块涵盖：

- 会话 CRUD 操作（创建、读取、更新、删除）
- 会话分叉（从指定消息点分支出新会话）
- 会话分享（生成/取消公开链接）
- 会话总结（压缩上下文，释放 Token 空间）
- 消息回退与重做（undo/redo）
- 活跃会话状态追踪（busy/idle/error/retry）
- 子会话关系管理与权限冒泡
- 项目作用域的会话列表（分页、搜索、时间分组）
- 会话统计（Token、费用、上下文使用率）

本模块不涵盖：

- 消息渲染与 Markdown 展示（由消息渲染模块负责）
- 权限请求弹窗 UI（由聊天界面模块负责）
- SSE 连接管理（由 API 通信层负责）

## 3. 功能需求

### FR-01：会话 CRUD 操作

| 属性   | 描述         |
| ------ | ------------ |
| 标识   | FR-01        |
| 名称   | 会话增删改查 |
| 优先级 | P0           |

**描述**：提供会话的创建、读取、更新、删除能力。

**要求**：

- 创建会话时可指定标题和工作目录，创建后自动返回会话元数据
- 获取会话列表支持分页（递增 limit 策略）、搜索关键词过滤、目录作用域过滤
- 获取单个会话时返回完整元数据（标题、目录、分享链接、回退状态、时间戳）
- 更新会话支持修改标题和归档时间
- 删除会话时同步清理子会话记录和排队消息，防止内存泄漏
- 列表加载支持滚动触底自动加载更多（分页）
- 搜索输入防抖（300ms），无搜索词时立即执行
- SSE 事件实时更新列表：session.created 追加到顶部，session.updated 更新并置顶，session.deleted 从本地移除
- 重连后清空列表并重新拉取

**验收标准**：

- 给定空列表，创建会话后新会话出现在列表顶部
- 给定 30 条会话，滚动到底部自动加载下一页
- 给定搜索词 "test"，列表仅显示标题包含 "test" 的会话
- 给定目录 A，列表仅返回目录 A 下的会话
- 删除会话后，其子会话记录同时被清理

### FR-02：会话分叉

| 属性   | 描述     |
| ------ | -------- |
| 标识   | FR-02    |
| 名称   | 会话分叉 |
| 优先级 | P1       |

**描述**：从现有会话的指定消息点创建分支会话，继承分叉点之前的所有消息历史。

**要求**：

- 分叉时指定消息 ID，新会话继承该消息之前的所有对话
- 用户消息分叉：新会话保留到指定用户消息（含），并将该消息内容预填充到输入框
- 助手消息分叉：找到该助手消息之后的下一条用户消息作为分叉点，确保助手回复被保留
- 分叉后自动导航到新会话
- 分叉点之后的消息不包含在新会话中

**验收标准**：

- 给定用户消息 M，分叉后新会话包含 M 及之前的所有消息，M 的内容预填充到输入框
- 给定助手消息 M，分叉后新会话包含 M 及之前的所有消息（含 M 之后的下一条用户消息）
- 分叉后浏览器 URL 自动切换到新会话

### FR-03：会话分享

| 属性   | 描述     |
| ------ | -------- |
| 标识   | FR-03    |
| 名称   | 会话分享 |
| 优先级 | P1       |

**描述**：为会话生成公开访问链接，允许他人查看对话内容。

**要求**：

- 调用分享 API 生成公开 URL
- 分享 URL 存储在会话元数据中，加载会话时自动获取
- 支持取消分享，撤销后 URL 失效
- 分享状态在会话切换时保持

**验收标准**：

- 给定未分享的会话，调用分享后返回可访问的 URL
- 给定已分享的会话，调用取消分享后 URL 不再有效
- 加载已分享的会话时，分享 URL 自动出现在元数据中

### FR-04：会话总结

| 属性   | 描述     |
| ------ | -------- |
| 标识   | FR-04    |
| 名称   | 会话总结 |
| 优先级 | P1       |

**描述**：压缩会话上下文，释放 Token 空间，允许长对话继续进行。

**要求**：

- 总结时指定提供商 ID 和模型 ID
- 支持自动模式（auto 参数）
- 总结操作为异步后台任务，不阻塞用户界面
- 总结完成后会话上下文被压缩，但对话历史保持完整

**验收标准**：

- 给定长会话，调用总结后上下文使用率下降
- 总结过程中用户可继续发送消息
- 总结失败不影响会话正常使用

### FR-05：消息回退与重做

| 属性   | 描述           |
| ------ | -------------- |
| 标识   | FR-05          |
| 名称   | 消息回退与重做 |
| 优先级 | P1             |

**描述**：支持撤销指定用户消息及其后的所有对话，并可逐步恢复被撤销的内容。

**要求**：

- 回退时指定用户消息 ID，该消息及之后的所有消息从视图中移除
- 回退后保存被撤销消息的完整内容（文本、附件、模型、Agent、变体），用于重做
- 重做时恢复最早一条被撤销的消息，并设置新的回退点
- 全部重做时清除所有回退状态，恢复到回退前的完整对话
- 清除回退状态不移除服务器端的回退标记，仅清理本地缓存
- 回退状态包含历史栈，支持多次逐步重做
- 加载会话时从服务器恢复回退状态

**验收标准**：

- 给定 5 条消息的会话，回退到第 3 条后，第 4、5 条不可见
- 回退后执行重做，第 4 条消息恢复，回退点移动到第 4 条
- 执行全部重做后，所有消息恢复，回退状态清除
- 切换会话后重新进入，回退状态正确恢复

### FR-06：活跃会话状态追踪

| 属性   | 描述         |
| ------ | ------------ |
| 标识   | FR-06        |
| 名称   | 活跃状态追踪 |
| 优先级 | P1           |

**描述**：实时追踪并展示所有会话的活跃状态，包括工作中、等待权限、等待回答、重试中等状态。

**要求**：

- 状态来源：GET /session/status 全量拉取 + SSE 事件实时更新
- 状态类型：busy（工作中）、idle（空闲）、retry（重试中）
- 等待中的权限/问题请求补充标记：pendingAction.type 为 permission 或 question
- 会话报告 idle 但仍有未回复的权限/问题请求时，延迟移出活跃列表
- 所有未回复的权限/问题请求均视为对应会话处于活跃状态
- 提供按 sessionId 查询单个条目、获取全部活跃列表、获取活跃计数三种查询方式
- 会话元信息（标题、目录）缓存与状态分离存储

**验收标准**：

- 给定会话正在处理消息，状态显示为 busy（工作中，绿色脉冲）
- 给定会话等待用户批准权限，状态显示为 busy + pendingAction.permission（黄色）
- 给定会话等待用户回答问题，状态显示为 busy + pendingAction.question（蓝色）
- 给定会话连接重试中，状态显示为 retry（黄色，含倒计时）
- 会话完成且无待处理请求后，从活跃列表移除

### FR-07：子会话管理

| 属性   | 描述       |
| ------ | ---------- |
| 标识   | FR-07      |
| 名称   | 子会话管理 |
| 优先级 | P1         |

**描述**：管理父会话与子会话（子 Agent 创建的任务）之间的层级关系。

**要求**：

- 子会话通过 parentID 字段关联父会话
- 注册子会话时建立 parentID -> children 映射，并存储子会话基本信息（标题、Agent 名称、状态、创建时间）
- 支持递归查询：获取 session 及其所有子孙 session 的 ID 列表（session family）
- 支持归属检查：判断某个 sessionId 是否属于指定 session 或其子孙
- 子会话状态更新：running、idle、error
- 权限请求冒泡：子会话的权限/问题请求显示在父会话界面
- 删除父会话时递归清理所有子会话记录
- 切换会话时自动加载子会话关系（如果 store 中尚未存在）
- 服务器切换时清空所有子会话数据

**验收标准**：

- 给定父会话 P 创建了子会话 C，C 出现在 P 的子会话列表中
- 给定子会话 C 的权限请求，该请求显示在父会话 P 的权限队列中
- 删除父会话 P 后，P 及其所有子孙的子会话记录被清理
- 查询 session family 返回父 session 及所有子孙 session 的 ID

### FR-08：项目作用域的会话列表

| 属性   | 描述           |
| ------ | -------------- |
| 标识   | FR-08          |

**要求**：

- 目录路径标准化：统一正斜杠、移除末尾斜杠

### FR-09：会话统计

| 属性   | 描述     |
| ------ | -------- |
| 标识   | FR-09    |
| 名称   | 会话统计 |
| 优先级 | P2       |

**描述**：计算并展示当前会话的 Token 消耗、费用和上下文使用率。

**要求**：

- 统计维度：inputTokens、outputTokens、reasoningTokens、cacheRead、cacheWrite、totalTokens
- 费用统计：累加每条助手消息的 cost 字段
- 上下文使用率：基于最后一条助手消息的总 Token 数与模型上下文限制的比值
- 仅统计有实际 Token 数据的消息（跳过 streaming 中的空数据）
- 上下文百分比上限 100%
- 统计结果随消息实时更新

**验收标准**：

- 给定 3 条助手消息均有 Token 数据，统计值为三者之和
- 给定 streaming 中的消息（tokens 为空），不计入统计
- 给定上下文限制 200000，已用 150000，显示 75%

### FR-10：会话加载与历史分页

| 属性   | 描述               |
| ------ | ------------------ |
| 标识   | FR-10              |
| 名称   | 会话加载与历史分页 |
| 优先级 | P0                 |

**描述**：管理单个会话的消息加载，包括初始加载和懒加载历史消息。

**要求**：

- 切换会话时优先使用缓存：如果缓存中已有完整加载且未过期的消息，直接使用
- 缓存未命中时从服务器拉取，初始加载使用默认消息数量限制
- 滚动到顶部时自动加载更多历史，每次递增固定批量大小
- 加载过程中维护 cursor（已请求消息数），避免重复请求
- 请求序列号机制：并发请求时仅采纳最后一次的结果
- 正在 streaming 的会话不覆盖已有消息，仅更新元数据
- force 模式（SSE 重连）下强制用服务器数据覆盖本地数据
- 本地 streaming 消息与服务器返回消息合并去重

**验收标准**：

- 给定已加载的会话 A，切换到 B 再切回 A，A 的消息直接从缓存恢复
- 给定 50 条消息的会话，初始加载 30 条，滚动到顶部后加载剩余 20 条
- 给定 streaming 中的会话，加载元数据时不覆盖正在显示的消息
- SSE 重连后，当前会话数据被服务器数据强制覆盖

### FR-11：会话消息 Store 管理

| 属性   | 描述            |
| ------ | --------------- |
| 标识   | FR-11           |
| 名称   | 消息 Store 管理 |
| 优先级 | P0              |

**描述**：集中管理所有会话的消息状态，支持多 session 独立存储、SSE 事件处理、回退状态管理。

**要求**：

- 每个 session 的消息独立存储在内存中
- 最多缓存固定数量的 session，超出时淘汰最久未访问的（受保护的 session 除外）
- 分屏模式下被查看的 session 受保护，不被淘汰
- SSE 事件直接修改对应 session 的消息，找不到对应 session 则丢弃
- 通知机制采用 requestAnimationFrame 批量合并，避免频繁触发 React 重渲染
- Delta 批量化：一帧内多次 mutable 修改仅产生一次数组拷贝
- 支持发送前快照回滚：发送失败时恢复到发送前状态
- 标记 session 为 stale：SSE 重连后标记所有 session 数据可能过期

**验收标准**：

- 给定 10 个 session 的缓存，新增第 11 个时淘汰最久未访问且未被保护的 session
- 给定分屏查看 session A，A 不会被淘汰
- 给定高频 SSE 事件，每帧仅触发一次 React 通知
- 发送消息失败后，消息列表恢复到发送前状态

### FR-12：会话消费者注册与 SSE 事件分发

| 属性   | 描述                 |
| ------ | -------------------- |
| 标识   | FR-12                |
| 名称   | 消费者注册与事件分发 |
| 优先级 | P1                   |

**描述**：多个窗格（pane）注册为会话消费者，SSE 事件按 sessionId 分发到对应的消费者回调。

**要求**：

- 每个 pane 注册时绑定一个 sessionId，事件仅分发到关注该 session 的 pane
- sessionId 变化时无需重新注册，仅更新关注目标
- 支持查询某个 session 是否有其他消费者（用于判断是否可以安全清理）
- 事件类型包括：permissionAsked、permissionReplied、questionAsked、questionReplied、questionRejected、scrollRequest、sessionIdle、sessionError、reconnected

**验收标准**：

- 给定两个 pane 关注不同 session，session A 的事件仅分发到 pane A
- 给定 pane 切换 sessionId，后续事件按新 sessionId 分发
- 给定 session 只有一个消费者，该 pane 关闭后可安全清理 session 数据

## 4. 关键实体

### 4.1 Session（会话）

会话的基本元数据，由后端返回。

| 属性      | 类型    | 说明                                    |
| --------- | ------- | --------------------------------------- |
| id        | string  | 会话唯一标识                            |
| title     | string  | 会话标题                                |

## 5. 状态流

### 5.1 会话生命周期状态机

```
                    ┌──────────┐
                    │  创建     │
                    └────┬─────┘
                         │
                         ▼
                    ┌──────────┐
              ┌─────│   idle   │──────┐
              │     └────┬─────┘      │
              │          │            │
              │          ▼            │
              │     ┌──────────┐      │
              │     │  busy    │      │
              │     └────┬─────┘      │
              │          │            │
              │    ┌─────┴──────┐     │
              │    ▼            ▼     │
              │ ┌──────┐   ┌───────┐  │
              │ │ idle │   │ retry │  │
              │ └──┬───┘   └───┬───┘  │
              │    │            │      │
              │    │     ┌──────┴───┐  │
              │    │     │ 成功/失败 │  │
              │    │     └──────┬───┘  │
              │    │            │      │
              │    ▼            ▼      │
              │  ┌──────────────────┐  │
              └──│  检查 pending    │──┘
                 │  请求？          │
                 └──────┬───────────┘
                        │
                 ┌──────┴───────┐
                 │              │
                 ▼              ▼
            有 pending      无 pending
            保持 busy       回到 idle
```

### 5.2 活跃状态详细流转

| 触发事件                   | 当前状态 | 新状态                     | 说明                              |
| -------------------------- | -------- | -------------------------- | --------------------------------- |
| 开始处理消息               | idle     | busy                       | 用户发送消息或执行命令            |
| 收到 idle 事件，无 pending | busy     | 移出活跃列表               | 会话完成工作                      |
| 收到 idle 事件，有 pending | busy     | 保持 busy（deferred idle） | 等待用户回复权限/问题             |
| 权限/问题请求到达          | idle     | busy + pendingAction       | 子会话的请求也会冒泡              |
| 权限/问题请求回复          | busy     | 检查是否还有其他 pending   | 无其他 pending 且 deferred 则移出 |
| 连接重试开始               | busy     | retry                      | 含 attempt、message、next 信息    |
| 重试成功                   | retry    | busy                       | 恢复正常处理                      |
| SSE 重连                   | 任意     | 标记 stale，重新加载       | 所有 session 标记为可能过期       |

### 5.3 消息回退状态流

```
正常对话 ──undo──▶ 回退状态（消息隐藏，历史栈保存）
                      │
                  redo│         redoAll
                      ▼            ▼
                部分恢复      完全恢复
                （新回退点）   （清除回退状态）
                      │
                  undo│
                      ▼
                新的回退状态
```

### 5.4 会话加载状态流

```
切换会话
    │
    ▼
检查缓存 ──有完整缓存──▶ 直接使用（loadState = loaded）
    │
    ▼
无缓存/不完整
    │
    ▼
loadState = loading
    │
    ├── 成功 ──▶ loadState = loaded
    │
    └── 失败 ──▶ loadState = error
```

## 6. 验收场景

### 场景 1：创建新会话

**前置条件**：用户已打开应用，当前有选中的工作目录

**步骤**：

1. 用户点击"新建会话"按钮
2. 系统调用创建会话 API，传入当前目录
3. 新会话出现在列表顶部

**预期结果**：

- 新会话 ID 由后端生成并返回
- 新会话出现在列表最上方
- SSE 事件 session.created 触发后，即使 API 调用未返回也能追加到列表
- 子会话（有 parentID）不出现在主列表中

### 场景 2：恢复历史会话

**前置条件**：存在已加载过的会话 A，包含 20 条消息

**步骤**：

1. 用户从侧边栏点击会话 A
2. 系统检查缓存

**预期结果**：

- 缓存命中时，20 条消息立即显示，无需网络请求
- 缓存未命中时，从服务器加载消息，显示加载动画
- 加载完成后，消息正确展示，滚动位置合理

### 场景 3：分叉会话

**前置条件**：当前会话有 5 条消息，用户想从第 3 条（用户消息）处分叉

**步骤**：

1. 用户点击第 3 条消息的分叉按钮
2. 系统调用分叉 API，传入第 3 条消息的 ID
3. 导航到新会话

**预期结果**：

- 新会话包含前 3 条消息
- 第 3 条消息的内容预填充到输入框
- 原会话不受影响，继续保留所有 5 条消息

### 场景 4：消息回退与重做

**前置条件**：当前会话有 5 条消息，用户想回退到第 2 条

**步骤**：

1. 用户对第 2 条消息执行回退
2. 第 3、4、5 条消息从视图移除
3. 用户执行一次重做
4. 用户执行全部重做

**预期结果**：

- 步骤 2 后，仅显示前 2 条消息，回退状态包含 3 条历史记录
- 步骤 3 后，第 3 条消息恢复，回退状态包含 2 条历史记录
- 步骤 4 后，所有 5 条消息恢复，回退状态清除

### 场景 5：活跃状态追踪

**前置条件**：两个会话正在工作中

**步骤**：

1. 会话 A 开始处理消息
2. 会话 A 请求文件编辑权限
3. 用户批准权限
4. 会话 A 完成工作

**预期结果**：

- 步骤 1 后，会话 A 显示为 busy（工作中，绿色脉冲）
- 步骤 2 后，会话 A 显示为 busy + awaitingPermission（黄色）
- 步骤 3 后，会话 A 恢复为 busy（工作中）
- 步骤 4 后，会话 A 从活跃列表移除

### 场景 6：项目切换与会话过滤

**前置条件**：存在项目 A（目录 /project-a）和项目 B（目录 /project-b），各有 5 个会话

**步骤**：

1. 用户切换到项目 A
2. 查看会话列表
3. 用户切换到项目 B
4. 查看会话列表

**预期结果**：

- 步骤 2 显示项目 A 的 5 个会话
- 步骤 4 显示项目 B 的 5 个会话
- 切换时列表自动刷新，分页 limit 重置

### 场景 7：子会话权限冒泡

**前置条件**：父会话 P 创建了子会话 C

**步骤**：

1. 子会话 C 请求文件编辑权限
2. 用户在父会话 P 的界面看到权限请求
3. 用户批准权限

**预期结果**：

- 步骤 2 中，权限请求显示在 P 的权限队列中，并标注来源为子会话 C
- 步骤 3 中，权限回复发送到子会话 C
- 子会话 C 继续执行被批准的操作

### 场景 8：会话分享

**前置条件**：当前会话有消息内容，未分享

**步骤**：

1. 用户点击分享按钮
2. 系统调用分享 API
3. 用户复制分享链接

- 步骤 3 链接复制到剪贴板
- 步骤 4 分享链接失效，URL 从会话元数据中清除

### 场景 9：会话搜索与时间分组

**前置条件**：存在 50 条会话，分布在不同的时间段

**步骤**：

1. 用户查看会话列表（无搜索词）
2. 用户在搜索框输入 "bug"
3. 用户清空搜索框

**预期结果**：

- 步骤 1 显示按时间分组的会话（今天、昨天、近 7 天、近 30 天、更早）
- 步骤 2 延迟 300ms 后执行搜索，显示标题包含 "bug" 的会话，不分组
- 步骤 3 立即恢复分组视图

### 场景 10：SSE 重连后数据恢复

- 步骤 3 后，会话列表清空并重新拉取

**前置条件**：侧边栏处于编辑模式，存在多个会话

## 9. 架构决策记录

### ADR-001：为什么会话列表采用递增 limit 而非游标分页

**决策**：会话列表使用递增 limit 策略（每次加载更多时增大 limit 值重新请求整个列表），而非传统的游标/页码分页。

**理由**：

- 与官方 WebUI 行为保持一致
- 避免游标分页在 SSE 实时更新下的数据不一致问题
- 会话列表总量通常不大，递增 limit 的性能开销可接受
- 简化本地状态管理，无需维护游标或页码

### ADR-002：为什么消息 Store 采用多 session 独立存储

**决策**：每个 session 的消息独立存储在 Map<string, SessionState> 中，而非全局单一消息列表。

**理由**：

- 支持分屏模式下同时查看多个会话
- SSE 事件按 sessionID 分发，天然适配独立存储
- 切换会话时可直接读取缓存，无需重新加载
- 支持 LRU 淘汰策略，控制内存占用

### ADR-003：为什么活跃状态 Store 与通知 Store 完全独立

**决策**：ActiveSessionStore 仅负责活跃状态追踪，NotificationStore 负责通知历史，两者不互相依赖。

**理由**：

- 职责单一，避免循环依赖
- 活跃状态是实时的（session 完成后即移除），通知是持久的（保留历史记录）
- 两者生命周期不同，合并会导致状态混乱

### ADR-004：为什么子会话的权限请求需要冒泡到父界面

**决策**：子 Agent 产生的权限/问题请求显示在父会话的界面中，而非子会话自己的界面。

**理由**：

- 子会话通常由父会话自动创建，用户可能不会主动查看子会话
- 权限请求需要用户及时响应，冒泡确保用户不会错过
- 通过 ChildSessionStore 的 session family 查询实现精确的请求归属过滤

### ADR-005：为什么通知采用 RAF 批量合并

**决策**：MessageStore 的状态变更通知使用 requestAnimationFrame 批量合并，而非每次变更立即通知。

**理由**：

- SSE 事件可能高频到达（如 token delta），逐次通知会导致 React 频繁重渲染
- RAF 确保每帧最多通知一次，与浏览器渲染周期同步
- Delta 批量化配合 dirtyMessages 集合，一帧内多次修改仅产生一次数组拷贝

## 10. 风险与缓解

| 风险                                | 影响                                   | 缓解措施                                        |
| ----------------------------------- | -------------------------------------- | ----------------------------------------------- |
| SSE 断流导致消息丢失                | 用户看不到自己发送的消息或 AI 回复     | 发送后 1.5 秒检查消息数量，未增加则主动拉取补齐 |
| 递增 limit 策略在大量会话时性能下降 | 列表加载变慢                           | 默认 limit 30，搜索态下交给服务端过滤           |
| 子会话记录内存泄漏                  | 删除父会话后子会话数据仍驻留内存       | 删除时递归调用 clearChildren 清理               |
| 多 pane 关注同一 session 时重复处理 | 权限请求被多次回复                     | 消费者注册机制确保事件仅分发到关注的 pane       |
| 回退状态与服务器不同步              | 本地回退历史与服务器 revert 标记不一致 | 加载会话时从服务器恢复 revert 状态              |
| 缓存淘汰导致已查看会话重新加载      | 切换回已查看会话时需要等待网络请求     | 分屏模式下保护当前查看的 session 不被淘汰       |
